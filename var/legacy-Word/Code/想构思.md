# 想构思

用户思维是发散的，随时想到随时说。模型的职责是把这些想法接住、整理成商业级设计。

---

## 0. 先对标，再发明（宏观优先）

用户提出的需求，**先判断最像哪一类已经成功的商业产品**（UI、功能、操作习惯），再设计。

| 步骤 | 做什么 |
|------|--------|
| 1. 归类 | 这句话本质是在要什么：写文档？管工程文件？聊天改稿？审阅对比？ |
| 2. 对标 | 点名 1～2 个商业产品（及具体界面区域），说明「相近在哪」 |
| 3. 建议 | **优先建议：仿照该产品长什么样**（菜单怎么收、标题在哪、快捷键习惯、多文档怎么切） |
| 4. 再裁剪 | 在对标骨架上，只加减我们产品必要的差异；禁止一上来自创 IDE/后台式交互 |

### 本产品默认对标地图（想到就用）

| 用户需求方向 | 优先对标 | 学什么 |
|--------------|----------|--------|
| 写稿、顶栏、保存/新建/打开、多文档 | **Word / WPS 文字** | 文件类菜单与办公套件习惯；文稿名居中；多稿页签；常见快捷键 |
| 工程内材料清单、版本副本 | **WPS 目录/文档页签** + 弱化资源管理器 | 分区列表，不做完整资源管理器 |
| 右侧问答改稿、Keep/Undo | **Cursor / 飞书智能伙伴类**（仅右侧） | 对话从属当前工程；主区仍是文档 |
| VS Code 本身 | **只当壳** | 不把命令面板、散落「⋯」、Explorer 当主教程路径 |

原则一句话：**需求长得像 Word，就先按 Word 讲清楚长什么样；不要先发明一排「新建｜文件｜保存｜⋯」。**

**本文件只写宏观要求与对标优先级。** 某一期菜单拆分、素材转换步骤等落地构思，写到 `specs/` 或其它短文，不要往这里堆。

## 模型必须做的

**1. 用大厂思维接收想法**
用户说的是"想法"，不是"需求文档"。模型要主动补全：
- 这个功能的边界在哪
- 影响哪些现有模块
- 有没有更好的实现路径
- **最像哪个商业产品，应先仿谁**

**2. 按商品级标准设计，不是能跑就行**
- 稳定：异常不崩溃，资源有上限，状态可恢复
- 可扩展：加新功能不改旧代码
- 可观测：运行状态能在 UI 里看到
- 可维护：改一处不牵连其他地方

**3. 先设计再动手**
想法 → 模型整理成设计方案（含对标产品）→ 用户确认 → 再写代码。
不允许"边想边写"，不允许用户说完就直接开干。

**4. 设计要具体到可落地**
不说"需要一个服务层"，要说：
- 新建哪个文件
- 加哪个函数
- 改哪个现有模块
- 数据库需不需要加字段
