# 架构设计规范

## 一、框架设计原则

### 1.1 分层架构

```
┌─────────────────────────────────────────────────────┐
│                    Presentation Layer               │
│              (API Handlers / Frontend)              │
├─────────────────────────────────────────────────────┤
│                    Service Layer                    │
│              (Business Logic / Engines)             │
├─────────────────────────────────────────────────────┤
│                    Data Layer                       │
│          (Database / Redis / External APIs)         │
├─────────────────────────────────────────────────────┤
│                    Infrastructure Layer              │
│           (Logging / Config / Networking)           │
└─────────────────────────────────────────────────────┘
```

**层级约束**:
- ❌ 禁止跨层调用（Presentation → Data 不可直接越到 Service 以外）
- ✅ 上层只能依赖下层
- ✅ 同层之间可以相互调用

### 1.2 模块依赖方向

```
    handlers (展示层)
         ↓
    services (服务层)
         ↓
   repositories (数据层)
         ↓
   models (数据模型)
```

**单向依赖原则**: 模块只能依赖其下层模块，禁止反向依赖或循环依赖。

## 二、模块化设计规范

### 2.1 模块划分原则

每个模块必须满足:

| 标准 | 说明 |
|------|------|
| **单一职责** | 一个模块只做一件事 |
| **高内聚** | 内部元素紧密相关 |
| **低耦合** | 模块之间依赖最小化 |
| **独立可测** | 不依赖其他模块可独立测试 |

## 三、低耦合设计

### 3.1 耦合类型与规避

| 耦合类型 | 危害等级 | 规避方式 |
|----------|----------|----------|
| 内容耦合 | 🔴 严重 | 禁止共享全局变量 |
| 公共耦合 | 🟠 高 | 减少共享数据结构 |
| 外部耦合 | 🟡 中 | 使用接口隔离外部依赖 |
| 数据耦合 | 🟢 低 | ✅ 推荐，通过参数传递 |

### 3.2 接口隔离原则 (ISP)

**定义**: 依赖方不应强迫依赖不需要的东西。

```
❌ 错误示例：一个大型接口
interface IWorker {
  processTask();
  sendEmail();
  generateReport();
  connectDB();
  makeCoffee();
}

✅ 正确示例：按职责拆分为小接口
interface TaskProcessor { processTask(): void; }
interface EmailSender { sendEmail(to: string): void; }
interface ReportGenerator { generateReport(): void; }
```

### 3.3 依赖注入 (DI)

**Rust** - 使用 trait 作为接口:
```rust
// 定义 trait 接口
trait ProxyProvider: Send + Sync {
    async fn get_proxy(&self) -> Result<Proxy, Error>;
    async fn refresh(&self) -> Result<(), Error>;
}

// 注入实现
struct ProxyDispatcher<P: ProxyProvider> {
    provider: Arc<P>,  // 通过 trait 对象注入
}

// 运行时注入具体实现
let dispatcher = ProxyDispatcher::new(Arc::new(HttpProxyProvider::new()));
```

**Go** - 构造函数注入:
```go
// 定义接口
type UserRepository interface {
    FindByID(id int64) (*User, error)
    Create(user *User) error
}

// 注入实现
type UserService struct {
    repo UserRepository  // 通过接口注入
}

func NewUserService(repo UserRepository) *UserService {
    return &UserService{repo: repo}
}
```

**前端** - 依赖注入:
```typescript
// React Context 注入
const ApiContext = createContext<ApiService | null>(null);

// Provider 注入
function ApiProvider({ children }: { children: React.ReactNode }) {
  const api = new ApiService();
  return <ApiContext.Provider value={api}>{children}</ApiContext.Provider>;
}

// 消费者使用
function MyComponent() {
  const api = useContext(ApiContext);
  // ...
}
```

### 3.4 事件驱动解耦

使用事件/消息进行模块间通信，减少直接依赖:

```
┌─────────────┐      事件       ┌─────────────┐
│   模块 A    │ ────────────→  │   模块 B    │
│             │                │             │
│  发送方     │                │  接收方     │
└─────────────┘                └─────────────┘

A 不需要知道 B 的存在，只需发布事件。
```

**示例** (Rust + Redis pub/sub):
```rust
// 发布事件
async fn on_task_complete(task_id: Uuid) {
    redis::publish("task:completed", task_id.to_string()).await;
}

// 订阅处理
async fn start_worker() {
    let mut sub = redis::subscribe("task:completed").await;
    while let Some(msg) = sub.next().await {
        handle_task_completed(msg).await;
    }
}
```

### 4.1 模块间通信规范

| 通信方式 | 适用场景 | 示例 |

## 五、代码重用规范

### 5.1 重用级别

| 级别 | 来源 | 重用方式 |
|------|------|----------|
| 🔵 工具函数 | 本模块 `utils/` | 直接 import |
| 🟢 通用组件 | `components/` | React 组件复用 |
| 🟡 服务层 | `services/` | 接口调用 |
| 🟠 基础设施 | 外部库 | 依赖注入 |

### 5.2 抽象层级

```
高层抽象 (重用优先)
├── 业务概念抽象
│   ├── TaskService (任务服务)
│   └── ProxyDispatcher (代理调度)
│
中间层抽象 (稳定性高)
├── Repository trait (数据访问接口)
├── EventBus (事件总线)
└── ConfigProvider (配置提供者)
│
底层实现 (经常变化)
├── PostgresRepo
├── RedisEventBus
└── EnvConfig
```

**原则**: 依赖稳定的高层抽象，绑定到不稳定但必要的底层实现。

## 六、扩展性设计

### 6.1 开闭原则 (OCP)

**定义**: 对扩展开放，对修改关闭。

```
❌ 违反 OCP: 修改原代码添加新功能
class FloodHandler {
    handle_http() { ... }
    handle_flood() { ... }
    // 添加新的攻击模式 → 必须修改这里
    handle_slow() { ... }
}

✅ 遵守 OCP: 通过扩展添加新功能
trait AttackMode {
    async fn execute(&self, ctx: &AttackContext);
}

struct HttpAttack;
struct FloodAttack;
struct SlowAttack;
// 添加新的攻击模式 → 只需新增实现类，无需修改现有代码
```

### 6.2 策略模式

```rust
// 定义攻击策略接口
trait AttackStrategy: Send + Sync {
    fn name(&self) -> &str;
    async fn execute(&self, req: &AttackRequest) -> Result<()>;
}

// 注入不同策略
struct AttackEngine {
    strategy: Arc<dyn AttackStrategy>,
}

impl AttackEngine {
    async fn run(&self, req: &AttackRequest) {
        tracing::info!("Running: {}", self.strategy.name());
        self.strategy.execute(req).await?;
    }
}
```

### 6.3 注册与发现模式

```rust
// 注册中心
struct StrategyRegistry {
    strategies: HashMap<String, Arc<dyn AttackStrategy>>,
}

impl StrategyRegistry {
    fn register(&mut self, name: &str, strategy: Arc<dyn AttackStrategy>) {
        self.strategies.insert(name.to_string(), strategy);
    }

    fn get(&self, name: &str) -> Option<Arc<dyn AttackStrategy>> {
        self.strategies.get(name).cloned()
    }
}
```

## 七、配置与状态管理

### 7.1 配置分层

| 层级 | 来源 | 优先级 | 示例 |
|------|------|--------|------|
| 环境变量 | 系统/容器 | 🔴 最高 | `DATABASE_URL` |
| CLI 参数 | 命令行 | 🟠 高 | `--port 8080` |
| 配置文件 | 项目文件 | 🟡 中 | `config.yaml` |
| 默认值 | 代码 | 🟢 低 | `port: 8080` |

### 7.2 状态管理原则

- **全局状态**: 使用 Context/Zustand，按业务领域拆分
- **组件状态**: React useState，局部使用
- **服务端状态**: React Query / SWR，缓存 + 同步

```
前端状态分类:
├── UI 状态       → useState / useReducer
├── 全局数据       → Context / Zustand
├── 服务端缓存     → React Query / SWR
└── URL 状态       → react-router
```

## 八、错误边界设计

### 8.1 错误传播

```
展示层 (Handler)
    ↑ 转换为用户友好错误
服务层 (Service)        ← 业务错误在此处理
    ↑ 返回 Result/Error
数据层 (Repository)     ← 底层错误在这里产生
```

### 8.2 Rust 错误层级

```rust
// 底层错误 (数据层产生)
enum RepoError {
    NotFound,
    DatabaseError(String),
    ConnectionError,
}

// 中层错误 (服务层产生)
enum ServiceError {
    TaskNotFound(Uuid),
    InvalidState(String),
    RepoError(RepoError),  // 包装底层错误
}

// 顶层错误 (API 层产生)
enum ApiError {
    BadRequest(String),
    InternalError(String),
    NotFound,
}
```

### 8.3 前端错误边界

```typescript
// React Error Boundary
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    // 记录错误日志
    logger.error(error, info);
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback />;
    }
    return this.props.children;
  }
}
```

## 九、代码审查 - 架构检查清单

### 模块化检查
- [ ] 模块职责是否单一？
- [ ] 模块间依赖方向是否正确（单向依赖）？
- [ ] 是否存在循环依赖？
- [ ] 接口是否按职责拆分（ISP）？

### 耦合检查
- [ ] 是否通过接口/事件通信而非直接调用？
- [ ] 是否使用了依赖注入？
- [ ] 共享状态是否最小化？

### 扩展性检查
- [ ] 新增功能是否需要修改现有代码？
- [ ] 是否使用了策略/注册模式处理变体？
- [ ] 是否遵守开闭原则？

### 重用检查
- [ ] 是否有重复代码可以抽象？
- [ ] 抽象层级是否合理（不要太浅/太深）？
- [ ] 公共组件是否已提取？

## 十、架构决策记录 (ADR)

重大架构决策需记录在 `docs/adr/` 目录:

```markdown
# ADR-001: 采用依赖注入管理服务依赖

## 状态
✅ 已接受

## 背景
Hub 服务中 handlers 直接创建 service 实例，导致：
- 单元测试困难（无法 mock）
- 服务替换成本高

## 决策
使用 trait 作为接口，通过 Arc<dyn Trait> 注入实现。

## 后果
- ✅ 测试更容易（可注入 mock 实现）
- ✅ 模块替换成本降低
- 🟡 增加少量代码（trait 定义）
```

## 十一、大厂决策思维

> 这一节是宏观判断原则，不绑定任何具体项目或语言。每次设计新功能、改造旧模块、或感觉"不对劲"时，对照这里想清楚再动手。

### 11.1 动手前先问三个问题

**① 这个改动属于哪一层？**

每次改代码前，先确认自己改的是哪一层的职责，然后只在那一层改：

| 你要做的事 | 应该在哪一层 |
|-----------|------------|
| 展示数据、接收用户输入 | Presentation（路由/Handler/页面） |
| 判断什么时候触发、状态怎么流转 | Service（业务逻辑层） |
| 实际干活（网络请求/文件操作/浏览器驱动） | Worker/Executor（执行层） |
| 读写数据库 | Repository/Data（数据层） |
| 后台定时运行 | 独立的后台线程/调度器 |

跨层了就是错的，不管多方便。

**② 状态从哪来，往哪去？**

任何有状态的业务对象（用户、任务、站点），在设计之初就要把完整的状态路径画出来：
- 初始状态是什么
- 合法的转移路径有哪些
- 每条失败分支是"永久排除"还是"可重试"
- 状态只能向前走，不允许随意回退

**③ 这个功能未来会变吗？**

- 会变 → 抽成接口/策略，用扩展代替修改（OCP）
- 不会变 → 直接实现，不要提前抽象（YAGNI）
- 不确定 → 保守实现，等真的需要再抽

---

### 11.2 后台任务的统一管理

所有需要后台定时执行的逻辑，统一在一个调度管理器里注册和启动，不允许在业务模块里随手启动线程。

**正确做法**：
```
scheduler.py / schedule_manager.py
  ├── thread_A: 每60秒检查暂停规则
  ├── thread_B: 每30秒扫描待处理任务 → 触发脚本生成
  └── thread_C: 每5分钟重试失败任务
```

**禁止**：在 Handler、Service、或 Worker 里 `threading.Thread(...).start()`。

**线程之间的通信**：只通过数据库（或消息队列），不共享内存变量，不直接 import 对方。

---

### 11.3 配置是唯一真相

项目里所有可调整的数值、路径、开关，只写在一个地方（`settings.py` / `config.go` / 环境变量），其他模块只读，不允许在业务代码里出现裸数字。

```
# ❌ 业务代码里的裸数字
rows = rows[:2]
time.sleep(30)

# ✅ 配置统一管理
rows = rows[:settings.BATCH_SIZE]
time.sleep(settings.POLL_INTERVAL)
```

**配置分层优先级**（高覆盖低）：
1. 环境变量（最高，生产部署用）
2. CLI 参数（调试用）
3. 配置文件（开发默认值）
4. 代码默认值（兜底）

---

### 11.4 数据库是唯一状态存储

不允许状态同时存在多处（内存变量 + JSON 文件 + 数据库三套）。

- **单一真相**：所有状态只写数据库，其他地方只读
- **JSON 文件**：只作为初始化加载源或兜底，不作为运行时状态存储
- **内存缓存**：只存只读的、可以随时从 DB 重建的数据

状态不一致是最难排查的 bug 来源。

---

### 11.5 资源必须有统一的生命周期管理

任何稀缺资源（数据库连接、浏览器实例、HTTP 连接池、文件句柄），都必须通过统一的池/管理器获取和释放，不允许各模块各自创建和销毁。

好处：
- 全局知道当前用了多少资源
- 超时/异常时统一清理
- 监控面板能实时展示资源占用

实现方式：Pool 模式 + context manager / RAII / with 语句，保证异常情况下也能释放。

---

### 11.6 什么时候不该做（Over-engineering 警戒线）

| 你在考虑 | 先问自己 | 原则 |
|---------|---------|------|
| 引入消息队列（Redis/RabbitMQ） | DB 轮询撑不住吗？ | 单机 DB 轮询通常够用，引入消息队列是为了跨机器 |
| 拆微服务 | 一台机器跑不下吗？ | 网络开销 > 进程切换开销，单机单进程优先 |
| 引入 ORM | 手写 SQL 维护不了吗？ | ORM 遮蔽 SQL，调试更难，简单项目用参数化查询即可 |
| 一次性大重构 | 能分步渐进吗？ | 大重构风险极高，优先"新代码放对层，旧代码慢慢迁移" |
| 新增数据库表 | 加字段能解决吗？ | 先加字段，表不够再建表 |
| 提前抽象 | 现在有几个实现？ | 只有一个实现就不要抽，等第二个出现再抽 |

---

### 11.7 新功能落点速查

> 随时想到随时改，但改之前先对照这张表确认落点，不乱放。

```
新功能是…
  ├── 展示数据给用户看           → 路由 Handler + 前端页面
  ├── 业务判断 / 状态流转        → Service 层（不存在时先放 Handler 里，后续迁移）
  ├── 具体执行（网络/文件/浏览器）→ Worker/Executor 模块
  ├── 数据读写                   → Repository/db 层，封装成函数，不直接写 SQL
  ├── 后台定时运行               → 调度管理器（统一注册线程）
  └── 配置项                     → settings / config 文件，不硬编码
```

## 十二、如何把散乱想法做成商品级设计

> 本节告诉模型**怎么做构思**，不是告诉它做什么。用户思维是发散的，模型的职责是接住想法、整理成可落地的设计。

### 12.1 接收想法的正确姿势

用户说的是"想法碎片"，不是"需求文档"。模型第一步是**主动补全**，而不是直接开写：

| 用户说 | 模型要追问/补全 |
|-------|--------------|
| "加个功能 X" | 谁用？什么情况下触发？成功是什么样？失败怎么处理？ |
| "改一下 Y" | 当前实现在哪个文件？改完影响哪些调用方？ |
| "加个页面 Z" | 数据从哪来？要不要新 API？状态要不要持久化？ |

不允许"用户说完就直接开干"。接到想法后，先整理出**功能边界 + 影响范围**，再决定怎么做。

---

### 12.2 设计前必须做的三件事

**① 读当前代码**
先搜（Grep/Glob），确认功能是否已经存在、在哪个文件、是什么状态。不允许没读代码就开始设计。

**② 画状态路径**
涉及状态变更的功能，先把完整路径列出来：
```
pending → doing → done
             └→ failed → retry → done
                              └→ abandoned
```
每个状态写清楚：谁设置、什么条件触发、能不能回退。

**③ 确认落点（参见 11.7）**
每个改动定位到：Handler / Service / Worker / Repository / 调度器 / 配置，不允许放错层。

---

### 12.3 提方案的格式

不允许只说"我打算做 X"，要具体到：

```
方案：[一句话描述]

改动范围：
- 新建文件：path/to/new_file.py
- 修改文件：path/to/existing.py — 加 function_name()
- DB 变更：login_sites 表加 username/password 字段
- 新增 API：GET /api/xxx — 返回 [{id, status}]

不改的东西：
- [明确说明哪些不动，防止范围蔓延]
```

用户确认方案后，再动手。

---

### 12.4 设计评审（自检清单）

写完方案草稿后，对照以下问题自检，不用逐条汇报，直接修掉：

- [ ] 是否改了本不应该动的文件？
- [ ] 有没有在业务代码里硬编码数值、路径、或 API 地址？
- [ ] 状态流转是否完整（包括失败分支和重试路径）？
- [ ] 后台线程是否统一在调度器里注册？
- [ ] 新功能加到了正确的层？（不是为了方便就放错地方）
- [ ] 有没有引入不必要的复杂度？（参见 11.6 Over-engineering 警戒线）

---

### 12.5 设计完成的标准

设计可以交付，必须满足：
1. **用户不需要猜** — 每个改动点都写明了文件路径 + 函数名 + DB 字段
2. **边界清晰** — 明确写了"不改什么"
3. **状态完整** — 所有分支（包括失败/重试）都有处理
4. **可以分步验证** — 每个步骤独立完成后都能测试，不是"全做完才能跑"
