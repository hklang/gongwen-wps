# 浏览器插件可行性研究（Edge / Chromium）

> 2026-08-11 · **研究案 → 产品意向已偏「浏览器为主壳」**（未开工）  
> 对标纪律：`Word/Code/想构思.md`  
> 铁律不变：稿在本地、不做网盘、模型对用户不可见。

---

## 0. 一句话

**面向机关用户：默认安装 Edge（或 Chrome）插件即可用；不要求装 VS Code。**  
壳 = 浏览器扩展页/侧栏 + 同一套 `editor.html` + 云中转 + 用户授权的本机工程夹。  
VS Code/Cursor 扩展可降为**内部调试壳 / 可选专业壳**，不再当获客主路径——「人人都会用浏览器，装插件有图文教程就行」。

## 1. 想法归类（你在要什么）

| 可能意图 | 本质 | 像不像咱们现在 |
|----------|------|----------------|
| A. 装个 Edge 插件就能写公文、读本机素材 | **独立公文编辑器壳** | ✅ 最接近现产品 |
| B. 在 Word Online / 政务网页面里侧栏改稿 | **网页附着助手**（Grammarly 型） | ❌ 另一条产品线 |
| C. 点一下把网页选中文字丢进咱们 AI | **剪贴板/选区伴侣** | 半套，丢工程能力 |
| D. 纯网页打开，不算插件 | **PWA / 本地页 + File System Access** | 能力接近 A，安装形态不同 |

下文默认讨论 **A（Edge 侧栏/独立页当壳）**；B/C 单开一节说明「疯狂但贵」。

## 2. 对标（先仿谁）

| 对标 | 学什么 | 别学什么 |
|------|--------|----------|
| **Word / WPS 文字**（主壳） | 顶栏、文稿名、多稿感；插件只是打开方式换了 | 不要做成浏览器设置页那种后台 |
| **Edge 侧栏 + Office 伴侣类** | 右侧常驻、从属当前任务 | 不要做成整页后台仪表盘 |
| **Notion / 在线编辑器 +「打开本地文件夹」**（Chromium File System Access） | 用户点一次授权工程目录，之后读写该树 | 不要假装有 VS Code 那种无感权限 |
| **Grammarly / 沉浸式翻译** | 内容脚本挂网页（仅当走 B 路线） | 不要用它当主写稿壳——公文工程能力会废 |
| **VS Code** | 仅内部联调可选 | 不要再当「用户必须装的编辑器」 |

原则：**需求长得像 Word；打开方式长得像「装个 Edge 扩展」——别做成开发者工具链。**

## 3. 现网能力 vs 浏览器能给什么

```text
现在：
  VS Code 扩展宿主
    ├─ 任意读写工作区 md / 素材 / 版本（Node fs）
    ├─ 嵌 editor.html（webview）
    ├─ 代打云中转 + 本机工具环
    └─ 本机 Python：docx↔md、导出等

浏览器扩展（Edge MV3）能给：
  ├─ 侧栏 / 独立扩展页嵌同一套 editor.html
  ├─ 登录短票、打 gongwen-relay（CORS 已开）
  ├─ File System Access：用户授权某个「工程目录」后可读可写
  └─ 权限可持久化（IndexedDB 存 directory handle）

浏览器弱项 / 缺口：
  ├─ 不能默默扫整盘（必须用户点选目录）——这是好事，也符合「稿不上云」叙事
  ├─ md↔docx、复杂转换：要 WASM / 云转换 / 或本机小助手（Native Messaging）
  ├─ 与 Cursor 同窗联动没有了
  └─ MV3 Service Worker 长任务、后台保活更挑
```

**结论：**  
「人机双写主界面 + 云端脑 + 本机工程夹」→ **浏览器做得到。**  
「无感工程集成 + 一键 docx 全链路」→ **VS Code 壳更强；浏览器要降配或加本地助手。**

## 4. 三种落点（利弊）

### 方案 A · Edge 公文壳（推荐若真做插件）

- **形态**：Edge 扩展；打开 **Side Panel** 或扩展页，铺满 `editor.html`。  
- **工程**：首次「打开工程」→ `showDirectoryPicker` → 授权含 `素材/`、`模板/`、`.gongwen/` 的目录。  
- **云**：沿用账号 / 额度 / 官方与「我的」模板 / AI。  
- **利**：触达不装 Cursor 的机关用户；安装像装「网页翻译」一样轻。  
- **弊**：转换/导出要另想办法；目录授权要教用户；双壳维护成本。  
- **改动面（若立项）**：新建 `Word/browser/`（MV3 manifest + sidepanel）；抽象「文件系统适配层」（现 `gongwenWorkspace` / bridge 的浏览器实现）；`editor.html` 少改。

### 方案 B · 网页附着助手（更「疯狂」，更贵）

- **形态**：Content Script 挂 Word Online / 指定政务域；侧栏改选中段落。  
- **利**：用户不用离开 Word。  
- **弊**：域权限、DOM 脆弱、难读本机素材夹、和「工程内公文」定位冲突；合规审查重。  
- **建议**：**不做主线**；最多远期试验。

### 方案 C · 不装插件，PWA / 固定站点页

- 同一套 File System Access，装到桌面「像 App」。  
- **利**：无商店审核；和 A 共用适配层。  
- **弊**：机关环境可能禁 PWA；感知弱于「Edge 应用商店里有个插件」。  
- **建议**：与 A **共用内核**，安装形态二选一或都做。

## 6. 产品意向（按你刚说的校准）

1. **主壳 = 浏览器插件**（优先 Edge，Chrome 同源可兼）。  
2. **用户故事**：打开浏览器 → 按说明装扩展 → 登录 →「打开本机工程文件夹」→ 写稿/AI。全程不出现 VS Code。  
3. **VS Code 外壳**：对用户宣传**可舍弃**；仓库里可暂留作开发自测，但不占获客与文档主路径。  
4. **只做方案 A**（独立写稿壳）；不挂 Word 网页（B）。  
5. **安装体验本身是产品**：一页「三步安装」（Edge 应用商店 / 开发者模式加载 .crx 或解压包——机关内网要另备离线包）。

### 舍弃 VS Code 后必须补上的三块（否则「简单」会变成「残废」）

| 缺口 | 浏览器怎么补 | 第一期能否砍 |
|------|--------------|--------------|
| 读写工程夹 | 首次选目录 + 记住授权 | **不能砍**（没有就丢差异化） |
| 登录/额度/模板/AI | 现成中转，扩展里直接打 | 不能砍 |
| docx 导入导出 | WASM / 云转换 / 以后再做 | **建议第一期只 md**，交稿用「导出 md / 复制」或后期加 |

### MVP（浏览器主壳第一刀）

- 要：安装说明、打开工程目录、读写 md、左侧工程列表、三 Tab AI、登录额度、官方/我的模板  
- 缓：docx 全链路、素材 pdf 转换、与 IDE 同级命令  
- 工期粗估：适配层 + MV3 + 目录授权 ≈ **2～4 周可内测**；商店包装与离线包另计

## 8. 能力对照表（供决策）

图例：✅ 能做好 · ⚠️ 能做但体验弱/要换做法 · ❌ 基本做不到或要另装本地助手才行

| 能力 | VS Code / Cursor 壳 | Edge / Chrome 插件壳 | 说明 |
|------|---------------------|----------------------|------|
| 安装门槛 | ⚠️ 要装 IDE | ✅ 人人会用浏览器 | 获客明显偏向插件 |
| 写 md、三 Tab AI、Keep/Undo | ✅ | ✅ | 同一套 `editor.html` |
| 登录 / 额度 / 标准·增强 | ✅ | ✅ | 打同一云中转 |
| 官方模板 / 我的云模板 | ✅ | ✅ | 已云端化 |
| 打开本机工程夹、读写 md | ✅ 无感跟工作区 | ⚠️ 首次要「选文件夹」授权，可记住 | 差异化还能保，但要教一次 |
| 侧栏列 文稿/素材/模板/版本 | ✅ | ⚠️ 仅限已授权目录内 | 不能扫整盘 |
| @引用、工具环读素材 md | ✅ | ✅（授权目录内） | 与上同前提 |
| 自动保存写回原文件 | ✅ | ✅（有目录写权限后） | File System Access 支持 |
| 系统剪贴板深度集成 | ✅ | ⚠️ 可用，权限/手势限制更多 | 一般够用 |
| 多窗口 / 跟 IDE 标签联动 | ✅ | ❌ 无 Cursor 标签那套 | 浏览器自己的多标签另说 |
| **打开/导入 docx→md** | ✅ 调本机 Python | ❌ 或 ⚠️ 很贵 | 插件不能直接跑你的 `md2docx.py`；要 WASM/云转换/本地小助手 |
| **导出 md→docx** | ✅ 同上 | ❌ 或 ⚠️ 很贵 | 同上 |
| 素材夹 docx/pdf/txt **一键转 md** | ✅ 本机转换 | ❌ 或 ⚠️ | pdf 更难；纯浏览器弱 |
| 「在资源管理器中显示」快照目录 | ✅ | ⚠️ 有限 | 不能当资源管理器管家 |
| 读任意盘符、无提示扫文件 | ✅（工作区权限内） | ❌ | 浏览器安全模型禁止；也符合隐私 |
| 后台常驻、系统托盘 | ⚠️ IDE 开着才有 | ❌ MV3 保活弱 | 不影响前台写稿 |
| 机关内网离线装 | ⚠️ VSIX | ⚠️ 离线 crx/解压包 + 说明 | 都要备离线通道 |
| 应用商店分发 | ❌（偏手动装扩展） | ✅ Edge/Chrome 商店（审核要过） | 也可跳过商店侧载 |

### 一句话拆分

| 类型 | 内容 |
|------|------|
| **插件不吃亏** | 写稿 UI、AI、账号、模板、本机 md 工程（选文件夹后） |
| **插件要改体验** | 「打开工程」= 选文件夹；不能假装已打开整个电脑 |
| **插件真正痛点** | **docx / pdf 转换与导出**——现网绑本机 Python，浏览器里没有等价物 |

### 决策用三档产品边界（任选）

| 档 | 对用户承诺 | 是否可纯插件交付 |
|----|------------|------------------|
| **档1 · 纯浏览器** | 只做 md 工程 + AI；交稿复制/下 md；docx 以后再说 | ✅ 推荐作第一期 |
| **档2 · 浏览器 + 云转换** | 上传片段到你们服务器转 docx（注意：碰铁律边缘，只能转格式不存稿） | ⚠️ 能做，要单独立规 |
| **档3 · 浏览器 + 本机小助手** | 另装一个静默小程序专跑 Python 转换 | ✅ 能力齐；安装包可把「会装 Python」藏起来 |

**建议拍板顺序：** 先定档1是否接受 → 再定要不要远期档2/档3；不要幻想「纯插件 = 现网 VS Code 能力 100% 平移」。

## 9. 本机小助手问答（复杂度 / Linux / 能否 Python）

### 9.1 复杂么？

| 部分 | 复杂度 | 说明 |
|------|--------|------|
| 转换逻辑 | **低** | 复用现有 `Word/tools/md2docx.py` 等 |
| 小助手进程 | **中低** | 收插件消息 → 调脚本 → 回传；MVP 约数百行级 |
| **安装与浏览器登记** | **中高** | Native Messaging 清单（Win 注册表 / Linux 配置目录）；对接 Edge、Chrome、国产浏览器 |
| 多系统交付 | **中** | Win 与 Linux 至少两套安装通道 |

难的是「装得上、找得到」，不是算法。

### 9.2 小助手可以是 Python 吗？

**可以。** 宿主可以是 Python 脚本，或用打包工具打成可执行文件（内嵌运行时）。

- 开发期：`python3 helper.py`  
- 交付期：建议打成 **单文件/安装包**，用户**不必自己会装 Python**  
- 转换仍调用现有 `tools/`，不重写一套  

### 9.3 Windows 和国产 Linux？

| 环境 | 可行性 | 注意 |
|------|--------|------|
| Windows + Edge/Chrome | ✅ 成熟 | 优先打通 |
| 国产 Linux（统信 / 麒麟等） | ✅ 原则上可以 | 浏览器多是 Chromium 系或自研壳，**未必有 Edge**；要按客户实际浏览器登记宿主 |
| 同一套 Python 转换代码 | ✅ | 跨平台；差别在启动与安装 |
| 一个安装包通吃所有系统 | ❌ | 至少 Win / Linux 分开；Linux 还要测具体发行版 |

### 9.4 用户要装什么（打包做好后）

| 路线 | 用户感知 |
|------|----------|
| 现网 VS Code | IDE + 扩展 +（docx 时）Python |
| 浏览器 + 小助手（交付包装好） | **扩展 + 一个傻瓜安装包**（助手±运行时） |
| 纯档1 | 只扩展 |

机关叙事可以是：「装浏览器插件 + 装公文助手」两步，比「先学 VS Code」更贴近公务员习惯；国产 Linux 要把目标浏览器写进适配清单。

## 10. 更大胆：自有桌面软件（改装 Code-OSS / 自研壳）

### 10.1 你在说什么

> 把 VS Code 那套拿来改装 → 变成**咱们自己的软件**；用户只装「公文客户端 +（内嵌）Python」，能进 VS Code 的机器，咱们原则上也能进。

对标：**Cursor / VSCodium / 各类行业定制 IDE**——都是 Code-OSS 或 Electron 壳，不是「让用户先装微软 VS Code」。

### 10.2 两条改法（别混）

| 改法 | 做法 | 工作量 | 结果 |
|------|------|--------|------|
| **A. 薄壳（推荐优先评估）** | 自研 Electron 窗：只嵌现有 `editor.html` + 本机 fs/Python 桥（把现在扩展宿主能力搬进自家 App） | **中** | 一个安装包；UI 仍是咱们公文界面，不是整棵 IDE |
| **B. 深改装 Code-OSS** | Fork [Code - OSS](https://github.com/microsoft/vscode)，预装咱们扩展、改名换皮、捆 Python | **高** | 真·「进得了 VS Code 的地方」；维护跟上游、体积大 |

注意：只能基于 **Code-OSS（MIT）** 改，**不能**拿带微软商标的 “VS Code” 成品换皮上架。

### 10.3 是否就没有「小助手 / 浏览器登记」问题了？

| 问题 | 自有桌面软件 |
|------|----------------|
| Native Messaging | ✅ **没有**——进程内直接调 Python，与现网扩展相同 |
| 用户先装 VS Code | ✅ **没有**——你就是那个软件 |
| 用户自己装 Python | ✅ 可捆进安装包，对外「只装一个」 |
| Win + 国产 Linux | ⚠️ **要自己打对应安装包并实测**；不是自动免疫信创限制 |
| 单位禁用非白名单软件 | ❌ 仍可能进不去（和 VS Code 一样要过信创清单） |

**机制上比「浏览器+小助手」干净；合规/上架仍要一台台环境过。**

### 10.4 和现网扩展的关系

- 现有 `gongwen-md` 扩展里的宿主逻辑（读写工程、调 `tools/`、打中转）**正是薄壳要吸收的核心**。  
- 不是推倒 `editor.html`，而是：**壳从「VS Code」换成「咱们 App」**。  
- 开发期仍可用 VS Code 跑扩展；交付物变成安装包。

### 10.5 复杂度实话

| 项 | 薄壳 A | 深 Fork B |
|----|--------|-----------|
| 做出能写稿+AI+docx 的安装包 | 数周～两月级（有现成 editor/扩展可搬） | 数月级起 |
| 长期维护 | 跟咱们自己的 Electron 版本 | 还要跟 Code 上游合入 |
| 体积 | 相对可控 | 往往 200MB+ 级 |
| 「能进 VS Code 的地方」 | 近似（同为桌面程序） | 更接近（同内核） |

### 10.6 研究结论（供拍板）

1. **想法成立**，且比浏览器绑小助手更贴「一个咱们自己的软件」。  
2. **优先论证薄壳 A**（Electron + 现网 editor + 捆 Python）；深 Fork B 只有在你明确要「完整 IDE 能力/扩展生态」时再上。  
3. 用户故事可收成：**下载《公文人机双写》安装包 → 打开就用**（内含转换运行时）。  
4. 国产 Linux = **发行版适配清单 + 安装包**，不是改装一次就永远兼容。  
5. 未立项前不写壳代码；若拍「走薄壳」，下一份规格写：安装包结构、fs/Python 桥 API、与 `gongwenEditor.js` 的迁移边界。

## 11. Word / WPS 插件可行性（再大胆一问）

### 11.1 归类

| 形态 | 用户在哪写 | 咱们是什么 |
|------|------------|------------|
| 现网 / 薄壳 / 浏览器 | **咱们的编辑器**（md 工程） | 主软件 |
| **Word / WPS 插件** | **仍在 Word/WPS 里** | 侧栏助手（改选区、出方案、插入） |

对标：**Grammarly / 金山同类加载项 / Microsoft 编辑器类侧栏**——不是再做一版 Word。

### 11.2 能不能做？

| 平台 | 技术路径 | 可行性 |
|------|----------|--------|
| **微软 Word（桌面/线上）** | Office.js 网页加载项（任务窗格） | ✅ 常见；跨 Win/Mac/部分 Web |
| **Word 老式 COM/VSTO** | C# 强桌面集成 | ✅ 仅 Windows；分发重 |
| **WPS 文字** | WPS JS 加载项（类 Office 但 API 不同） | ✅ 国内机关很常见；要单独适配 |
| **一套代码通吃 Word+WPS** | — | ⚠️ **不能指望**；UI 可共，宿主 API 两套 |

### 11.3 和现网能力差在哪（关键）

| 能力 | md 工程壳（VS Code/薄壳/浏览器） | Word/WPS 插件 |
|------|--------------------------------|---------------|
| 用户学习成本 | 要打开「另一个软件」或选文件夹 | ✅ **最低**：人本来就在用 Word/WPS |
| 正文存在哪 | 本机 md | Word/WPS 文档本身 |
| 侧栏 AI、选区改稿、多套方案 | ✅（对 md） | ✅（对选区/文档，要重接读写） |
| 工程「素材/」据实写数、工具环扫夹 | ✅ 强项 | ⚠️ 网页加载项很难随便扫盘；桌面加载项可做但另套权限 |
| 官方/我的云模板 | ✅ | ⚠️ 可「插入到光标」；不是落地 `模板/` 工程 |
| md↔docx 转换 | 需要 Python/工具 | **往往不需要**——人就在 docx 里 |
| 复用现有 `editor.html` 整页 | ✅ | ❌ 只能抽右侧 AI；不能整页当 Word |
| 国产 Linux + 金山 WPS | 薄壳要自适配 | ✅ **WPS 插件往往更贴机关** |
| 开发/上架 | 自控 | 商店审核、域名 HTTPS、企业侧载策略 |

### 11.4 利弊一句话

- **利**：获客路径几乎等于「会用 Word/WPS」；交稿格式天然是 docx；少纠结 Python 转换。  
- **弊**：产品从「本地 md 工程编辑器」变成「办公套件里的 AI 侧栏」；**素材夹、版本夹、双轨模板落地**等现网主差异要砍或重做；Word 与 WPS **两套适配**；和薄壳不是同一条交付。

### 11.5 和薄壳怎么选（别幻想「一个插件全包」）

| 若你最在意… | 更该走… |
|-------------|----------|
| 本机工程、素材据实、自己的软件品牌、装一个客户端 | **薄壳** |
| 机关已经整天泡在 WPS/Word，只想侧栏帮改 | **WPS/Word 加载项** |
| 两者都要 | **双产品**：薄壳 = 专业工程版；加载项 = 轻量改稿版（云账号可共用） |

### 11.6 研究口径

1. **能做**，尤其 **WPS 加载项**对国产机关叙事很香。  
2. **不是**把现在扩展「改个清单就能进 WPS」；要按选区/文档对象重接 AI，工程能力会变瘦。  
3. 与薄壳 **可并行规划、不可混成一个安装包指望通吃**。  
4. 若拍 WPS 优先：下一份规格单独写「任务窗格信息架构 + 读写选区 API + 素材怎么给（粘贴/@云模板/选本地文件）」；**先规格后代码**。

## 12. WPS 插件：准备 / 发布 / 卡点（落地清单）

> **尖刀实证 + 可借鉴开源清单（2026-08-11）**：见同目录 [`2026-08-11-WPS加载项尖刀与借鉴.md`](./2026-08-11-WPS加载项尖刀与借鉴.md)。

### 12.1 你需要准备什么

| 类别 | 要有什么 | 备注 |
|------|----------|------|
| 开发机 | 已装 **WPS（建议企业版/专业版，版本别太旧）**、Node.js、`npm i -g wpsjs` | 官方脚手架：`wpsjs create` / `debug` |
| 产品范围 | 先定 MVP：侧栏登录 + AI 改选区 + 插模板；**不做**整页 md 工程 | 避免范围膨胀 |
| 后端 | 现成 `gongwen-relay`（短票、chat/suggest）+ HTTPS 可达 | 加载项网页要能打你们的 API（CORS 已有基础） |
| 托管 | 一台能挂静态站的服务器（公网或机关内网） | 放加载项包 + 安装页 |
| 证书 | **HTTPS**（公网证书或内网可信 CA） | 见下方卡点 |
| 测试机 | Win 企业 WPS 一台；若要信创再加 Linux WPS 一台 | 版本号记清楚 |
| 法务/商务（可选） | 若走「二次打包进客户 WPS 安装包」需对接金山/集成商 | 机关大单常见，周期长 |

### 12.2 怎么发布（推荐路径）

官方推荐 **publish 模式**（不要再靠改 `oem.ini` 的旧办法，新版本已限制）：

```text
开发：wpsjs create → 写任务窗格 → wpsjs debug
打包：wpsjs publish（填加载项资源服务器地址）
部署：
  · wps-addon-build/   → 服务器 A（加载项静态资源：ribbon.xml、页面等）
  · wps-addon-publish/ → 服务器 B（publish.html 安装引导页，可与 A 同机）
用户：浏览器打开 https://你们的域/publish.html → 点安装
      → 本机生成 publish.xml（Win: %appdata%/kingsoft/wps/jsaddons
                              Linux: ~/.local/share/Kingsoft/wps/jsaddons）
      → 打开 WPS 文字即加载
```

适用：只交付 WPS 基础包、松耦合集成。  
版本门槛（官方表述）：Windows 企业版约 20200425 分支后；Linux 企业版约 20200530 分支后。

**备选 · jsplugins / 二次打包**：把 `JSPluginsServer` 打进客户定制 WPS 安装包——适合集成商整包交付；新版本限制更多，**非首选**。

### 12.3 用户侧最短话术

1. 本机已装符合版本的 WPS 文字  
2. 用浏览器打开你们给的 **安装页（HTTPS）**  
3. 点「安装」并允许调起本地 WPS  
4. 打开 WPS → 功能区出现咱们按钮 → 开任务窗格登录使用  

### 12.4 容易卡住的地方（按概率）

| 卡点 | 严重度 | 怎么缓解 |
|------|--------|----------|
| **publish.html 非 HTTPS**，浏览器拦截访问本机 `127.0.0.1`（装不上） | 高 | 安装页必须 HTTPS；内网备可信证书 |
| 客户 WPS 是**个人版/过旧企业版**，加载项行为异常 | 高 | 发布前写清「最低版本」；先测客户镜像 |
| **信创 Linux WPS** 版本/权限与 Win 不一致 | 中高 | 单列适配机；别口头承诺「全 Linux」 |
| 内网不能访问你们托管地址 | 中 | 内网镜像部署 build+publish；或离线包模式 |
| 读写选区/复杂排版 API 与预期不符 | 中 | MVP 先做「纯文本选区替换」；排版后期加 |
| 想扫本机「素材/」工程夹 | 中 | 加载项弱；改成选文件/粘贴/只用云模板 |
| 走二次打包进定制 WPS | 中（商务） | 周期长，需集成商；别当第一期路径 |
| CORS / 登录页嵌在任务窗格 | 低～中 | 中转已允许跨域；注意 Cookie/短票存 PluginStorage |

### 12.5 和「薄壳安装包」对比（发布难度）

| | WPS 插件 | 薄壳客户端 |
|--|----------|------------|
| 用户安装 | 打开网页点安装（依赖本机 WPS） | 跑一个安装包 |
| 你们要维护 | 静态资源站 + HTTPS + 版本说明 | Win/Linux 安装包 + 更新通道 |
| 最大坑 | HTTPS/版本/信创 WPS | 打包体积与系统适配 |

**第一期若走 WPS：准备清单的核心就是「企业版 WPS 测试机 + HTTPS 静态站 + 收窄 MVP」。**
