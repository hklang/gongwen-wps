# 想构思

先看 `总.md` 确认该打开本文件。

用户思维是发散的。模型把碎片收成可拍板的设计，不直接开写。

**建议要短；有选项必须标一个「推荐」。**  
流水线：本文件 → `记方案.md` → `写代码.md` → `做测试.md` → `推版本.md`。

---

## 1. 先对标，再裁剪

| 步骤 | 做什么 |
|------|--------|
| 归类 | 这句话本质在要什么（文档、清单、对话、审阅、设置…） |
| 对标 | 点名 1～2 个成熟商业产品及界面区域，说明相近在哪 |
| 建议 | **优先仿该产品骨架**（菜单、标题、快捷键、多实体怎么切） |
| 裁剪 | 只加减本产品必要差异；禁止一上来自创生疏交互 |

原则：**需求像谁，先按谁讲清楚长什么样。**

---

## 2. 什么规模要完整构思

| 规模 | 怎么做 |
|------|--------|
| 单点 bug、文案、已有规格里的小修补 | 一句话范围 + 动手；仍要写清怎么验 |
| 新交互、跨模块、改旧约定、有 2～3 个做法 | 必须对标 + 方案，确认后再写 |

---

## 3. 接住想法（用户说的不是需求文档）

- 边界在哪、本期**不做**是什么
- 影响哪些现有模块
- 有没有更好的路径
- 最像哪个商业产品，应先仿谁
- **做成什么样**：用户看见/操作到什么算过；失败时怎样

商品级：稳定、可扩展、可观测、可维护。能跑不等于能交。

不允许边想边写。构思停在「长什么样、做/不做、怎么算过」。文件级落点进规格。

---

## 4. 提方案时

- 列 2～3 个做法 → 标「推荐」→ 等拍板
- 写清非目标
- 改旧约定必须先说，禁止默默改

---

## 何时去看总要求（可跳过）

默认不看。仅当：要新开一层/新模块、模块怎么通信不确定、耦合明显变重。  
读 `总要求/架构设计规范.md`，只取原则。
