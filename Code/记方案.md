# 记方案 Checklist

**给建议要简明扼要，别啰嗦；有选项时必须标一个「推荐」。**

**写代码之前先看 `写代码.md`；推 GitHub 之前先看 `推版本.md`。**

方案没想清、没记清，禁止开写代码。

---

## 0. 路径统一（禁止乱存）

| | 约定 |
|--|------|
| **目录** | 仓库根下 **`specs/`**（相对本项目；不另开 `方案/` `docs/plans/` 等） |
| **文件名** | `YYYY-MM-DD-序号-主题短名.md`（同日 01 起；例：`2026-08-13-05-WPS版本夹双轨与恢复.md`） |
| **一题一文** | 同一问题只维护**这一份**；禁止 `…-v2` / `…-最终` / `…-副本` |
| **再研究** | **改原文件**：更新已定/已完成/未完成/存疑；文首「修订」加一行日期+改了啥；**不改文件名** |
| **同日多题** | 主题不同 → 多文件，序号接着编；主题相同 → 仍改原文件，不新开 |
| **新建前** | 先搜 `specs/` 有没有同主题；有就改它 |

文首建议三行：`日期` / `状态` / `修订`（再研究时往下追加，不另存盘）。

---

## 1. 先想清，再落笔

- 一句话问题是什么
- 对标谁（见 `想构思.md`）
- 本期做 / 不做（非目标写死）
- 有选项时：列 2～3 个 → **标「推荐」** → 等用户拍板

## 2. 记什么（规格里必须能扫到）

| 栏 | 写什么 |
|----|--------|
| **已定** | 拍过板、可验收的约定 |
| **已完成** | 已落地、可点验的能力 |
| **未完成** | 还没做，或做了一半 |
| **存疑** | 未拍板 / 行为不稳定 / 待核实 |
| **模型建议** | 简短；有选项必带「推荐」 |

状态用：`已定` / `进行中` / `已完成` / `存疑` / `不做`。

## 3. 怎么记

- 短句、表格式；禁止长篇复述聊天
- 改结论就改**同一份** `specs/…`，别只活在对话里
- 存疑单独挂起，不假装已定
- 与代码不一致时：**先改规格或先标存疑**，禁止默默分叉

## 4. 回答用户时

- 先给结论或「推荐」
- 进度用三行扫：已完成 / 未完成 / 存疑
- 细节指向 `specs/YYYY-MM-DD-序号-主题.md`，不在聊天里堆全文

## 5. 何时可以写代码

- [ ] 推荐方案已获同意（或用户明确「你定」）
- [ ] 已定 / 未完成 / 存疑 已写入 **`specs/` 对应一文**
- [ ] 验收标准可测
- [ ] **先通读 `写代码.md`，再动手**

推仓库前：**先通读 `推版本.md`，再 commit / push。**

## 6. 和另外三份的关系

| 文件 | 管什么 |
|------|--------|
| `想构思.md` | 对标与产品方向 |
| **`记方案.md`** | 方案是否想清、记清、状态清；**只进 `specs/`** |
| `写代码.md` | 怎么改代码 |
| `推版本.md` | 怎么提交推送 |
